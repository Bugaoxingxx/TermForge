## 发现

### [P2] `forceInputSimulator` 标志无人使用，Win32 回退路径完全未被执行

- 位置：`tests/AgentTerminal.UITests/Pages/MdiChildWindowPage.cs:52-89`
- 问题：`DragBy` / `DoubleClickTitleBar` / `ResizeBottomRight` 新增了 `forceInputSimulator` 参数，但全仓无任何调用点传 `true`（grep 仅命中定义处）。`MdiChildWindow` 的自动化对等体始终暴露 `ITransformProvider` / `IWindowProvider`，因此这些方法永远走 UIA 模式，`InputSimulator.Drag` / `DoubleClick` 在整个测试套件中一次都不会执行。
- 影响：本次改动的 `InputSimulator` 验证逻辑，以及此前几次提交修复的“物理输入成功后双重注入”问题，至今没有任何执行中的测试覆盖。提交信息声称该标志用于“support physical/Win32 fallback testing”，但实际是死参数。
- 建议：新增一个显式传 `forceInputSimulator: true` 的用例覆盖物理/Win32 回退路径；或明确 `InputSimulator` 仅为备用路径并移除未验证的复杂度。

### [P2] “位移判定成功”会把合法的钳制/空操作误判为失败，触发二次注入

- 位置：`tests/AgentTerminal.UITests/Infrastructure/InputSimulator.cs:68-78`、`124-133`
- 问题：物理手势执行后以 `bounds 是否变化` 作为成功信号，未变化即掉入 Win32 回退再执行一次。但“物理拖动成功但被钳制”（窗口已在边界，继续向边界外拖导致位置不变）是合法结果，会被判为失败而二次注入——正是最初审阅要消除的双重注入，在边界场景下有条件地复活。`bounds 未变`混淆了“手势未注册（应回退）”与“手势已注册但结果为钳制/空操作（不应回退）”两种情况。`DoubleClick` 以宿主窗口尺寸/位置变化判定，边界态（双击未改变尺寸）同样会误回退再点一次。
- 影响：若 `forceInputSimulator` 被启用，边界拖拽/双击将出现环境相关的重复手势与假阳性；与本提交“reliable Win32 fallback”的目标相悖。
- 建议：改用能区分“输入是否真的发生”的信号（如手势前后光标状态、或结合钳制预期），而非以最终 bounds 变化作为唯一成功条件。

### [P3] 60/40 钳制位断言用物理像素对比 DIP，非 100% 缩放会误报

- 位置：`tests/AgentTerminal.UITests/Specs/MdiWorkbenchLayoutTests.cs:218-224`
- 问题：产品钳制为 `canvas.ActualWidth - 60` / `canvas.ActualHeight - 40`（DIP 单位），而 `BoundingRectangle` 为物理像素。在 125% / 150% 缩放下，60/40 DIP 折算为 75/90、50/60 物理像素，偏差超过 15px 容差，断言将失败。
- 影响：隐藏的环境依赖；CI 若锁定 100% 缩放则不触发。交集断言（`>= 50/30`）较稳，不受此影响。
- 建议：将期望值按 DPI 缩放换算，或放宽为按比例的容差；或在测试初始化时断言/强制 100% 缩放。
