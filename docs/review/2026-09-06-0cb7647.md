## 结论

**建议：请求修改（Request changes）—— 直接删除 `InputSimulator`。**

DPI 换算修复正确干净（P3 已闭合）。但本次对 `InputSimulator` 的改动引入了新的逻辑回归：`FindWindow` 改为上溯到顶层原生窗口后，`DoubleClick` 的状态变化检测失效；新增的 `GetCursorPos` 二次判定在交互桌面上近乎恒真，等于关闭了“物理输入失败→回退”的检测能力。

根本症结是：`InputSimulator` 整条链路无任何测试执行（见 [P0]），却被反复雕琢——上述两处回归正是没测试才没被发现。与其继续在死代码里堆逻辑，**审阅结论是直接删除 `InputSimulator` 及其在 `MdiChildWindowPage` 中的兜底调用**。删除后，上面两处 `InputSimulator` 内部回归自动消失，无需再修。

## 发现

### [P1] `FindWindow` 改动使 `DoubleClick` 的状态变化检测失效（删除 `InputSimulator` 后消失）

- 位置：`tests/AgentTerminal.UITests/Infrastructure/InputSimulator.cs:37-56`、`145-161`
- 问题：`MdiChildWindow` 是 UserControl，自动化对等体报 `ControlType.Window` 但无原生 HWND。改动后 `FindWindow` 跳过它、上溯到顶层 OS 主窗口（对 Win32 回退取 `hWnd` 是改进）。但 `DoubleClick` 用同一个 `window` 做成功判定：MDI 子窗口最大化时顶层主窗口尺寸/位置不变，`hasChanged` 恒为 `false`，上一轮刚加的“双击是否切实改变窗口状态”检测被废掉。
- 影响：`DoubleClick` 的状态变化判定形同虚设，只能依赖下面恒真的光标判定兜底。
- 建议：成功判定应基于 MDI 子窗口（`WindowVisualState` / 子窗口 bounds），而非顶层主窗口；或将“查找回退用的原生窗口”与“判定用的目标元素”解耦为两个变量。

### [P1] `GetCursorPos` 二次判定在交互桌面上近乎恒真，失去失败检测能力（删除 `InputSimulator` 后消失）

- 位置：`tests/AgentTerminal.UITests/Infrastructure/InputSimulator.cs:91-101`、`163-171`
- 问题：`Mouse.MoveTo(endScreen)` / `Mouse.DoubleClick(screenPt)` 本身已把光标设到终点/点击点，`GetCursorPos` 读回的就是该位置，`distSq≈0` 恒真返回。这与两轮前标记的“用 `SetCursorPos` 回读当成功条件”属同一类问题：证明的是“移动了光标”，而非“手势对目标生效”。结合上一条，`DoubleClick` 仅剩此恒真路径，物理双击即便未注册也永不回退到 Win32。
- 影响：避免了交互桌面上的二次注入（本次目标达成），但同时丧失了检测真实派发失败并回退的能力。
- 建议：以目标效果（位移 / `WindowVisualState` 改变）作为成功信号；光标位置不能作为手势生效的证据。

### [P0] 直接删除 `InputSimulator` —— 整条链路无任何测试执行

- 位置：`tests/AgentTerminal.UITests/Infrastructure/InputSimulator.cs`（整文件）、`tests/AgentTerminal.UITests/Pages/MdiChildWindowPage.cs:52-110`
- 问题：全仓仅 `MdiChildWindowPage` 三处调用 `InputSimulator`（`DragBy` / `DoubleClickTitleBar` / `ResizeBottomRight`），且均位于 `_element.Patterns.Transform.IsSupported` / `Patterns.Window.IsSupported` 判断的兜底分支。`MdiChildWindow` 的自动化对等体（`MdiChildWindowAutomationPeer`，见 `MdiChildWindow.xaml.cs`）恒暴露 `ITransformProvider` / `IWindowProvider`，因此这些分支永远走标准 UIA（`Transform.Move` / `Transform.Resize` / `SetWindowVisualState`），`InputSimulator` 一行都不会执行。
- 影响：`InputSimulator` 及本轮新增的 `GetCursorPos`、改写的 Win32 双击序列、`FindWindow` 逻辑全是无测试覆盖的死代码，却在被持续修改并反复引入回归。
- 建议（结论性）：**删除 `InputSimulator.cs` 整个文件，并移除 `MdiChildWindowPage` 中三处 `InputSimulator.Drag/DoubleClick` 兜底调用**。删除后：
  1. `DragBy` / `ResizeBottomRight` / `DoubleClickTitleBar` 保留 UIA 分支即可；若确需防御「模式不可用」，将兜底改为 `throw new InvalidOperationException(...)` 明确失败，而非静默走一段不可靠的模拟逻辑。
  2. 一并清理 `MdiChildWindowPage` 顶部对 `AgentTerminal.UITests.Infrastructure`（若仅为 `InputSimulator`）的 using。
  3. 本文件 [P1]（`FindWindow`）与 [P1]（`GetCursorPos`）两处回归随之消失，无需单独修复。
- 复核：删除前确认无其它调用点（当前 grep 仅命中 `MdiChildWindowPage`）；若后续新增无 UIA 模式的可交互控件再按需引入经过测试的实现。

### [P3] 大幅越界拖拽终点被裁到屏幕外会误触发回退

- 位置：`tests/AgentTerminal.UITests/Infrastructure/InputSimulator.cs:91-101`
- 问题：`endScreen` 对 `-800/+3000` 这类拖拽落在屏幕外，OS `SetCursorPos` 将光标裁到屏幕边缘，`GetCursorPos != endScreen` → `distSq>100`。若此时窗口恰好未位移（已在边界），会掉进 Win32 回退再拖一次。
- 影响：属窄边界情形；现有钳制测试因 bounds 会变（路径 a 先返回）暂不触发。
- 建议：终点先按虚拟屏幕边界裁剪后再比较，或统一改用目标效果判定。
